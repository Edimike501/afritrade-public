# Infrastructure & Zero-Cost Cloud Deployment Guide

AfriTrade Connect is architected for **zero infrastructure cost ($0/month)** across development, testing, staging, and production environments using free-tier serverless and cloud providers.

---

## 1. Hosting Architecture Overview

| Component | Provider & Free Option | Role & Configuration |
| :--- | :--- | :--- |
| **PostgreSQL** | [Neon Serverless PostgreSQL](https://neon.tech) | Primary transactional database with branching (`staging` and `main`). |
| **Redis Cache** | [Upstash Redis](https://upstash.com) | Low-latency in-memory session metadata, refresh token hashing, and RTR reuse detection (RULES §18). |
| **Private Document Vault** | [Cloudflare R2](https://developers.cloudflare.com/r2/) | Zero-egress free-tier S3-compatible object storage (10 GB/mo free) for private KYB verification documents, served exclusively via short-lived (5m) signed URLs (`STORAGE_MODE=simulated \| r2`). |
| **Backend API** | [Render Web Service](https://render.com) | NestJS modular monolith with automated deploy hooks and commit tracking. |
| **Web Marketplace** | [Vercel](https://vercel.com) | Next.js App Router buyer/supplier application with preview/staging aliases and edge CDN. |
| **Admin Console** | [Vercel](https://vercel.com) | Next.js App Router platform oversight console. |
| **CI/CD Pipeline** | GitHub Actions | Single unified workflow (`.github/workflows/deploy.yml`) with automated migration, seeding, and smoke testing. |

## 2. Platform Setup & Configuration

### 2.1 Neon Serverless PostgreSQL
Neon provides copy-on-write branching for serverless Postgres without paying for separate staging databases.

1. **Project Creation**: Create project `afritrade-connect` in [console.neon.tech](https://console.neon.tech).
2. **Branches**:
   - `main`: Production database branch.
   - `staging`: Dedicated staging database branch (parent: `main`).
   - `ci/*`: Ephemeral branches automatically created and deleted during PR integration testing runs.
3. **Connection Strings**:
   - **Direct (Unpooled)**: Used by migrations (`prisma migrate deploy`) to avoid pgbouncer advisory locking limits:
     `postgresql://[user]:[password]@[endpoint].neon.tech/[dbname]?sslmode=require`
   - **Pooled (pgBouncer)**: Used by Render API services at runtime:
     `postgresql://[user]:[password]@[endpoint]-pooler.neon.tech/[dbname]?sslmode=require`

### 2.2 Upstash Redis
Token revocation and RTR token family invalidation are backed by Redis.

1. In [console.upstash.com](https://console.upstash.com), create two free databases:
   - `afritrade-redis-staging`
   - `afritrade-redis-prod`
2. Select TLS-enabled connection string (`rediss://default:[password]@[endpoint].upstash.io:6379`) and configure as `REDIS_URL`.

### 2.2b Cloudflare R2 (Private KYB Document Storage)
Cloudflare R2 provides 10 GB/month of free S3-compatible object storage with zero egress fees.

1. In the Cloudflare Dashboard ➔ **R2 Object Storage**, create a private bucket (e.g., `afritrade-kyb-private`).
2. Generate an R2 API Token with **Object Read & Write** permissions scoped to `afritrade-kyb-private`.
3. Configure environment variables on the API service when enabling live R2 storage:
   - `STORAGE_MODE=r2` (defaults to `simulated` in local dev/CI so zero external network calls are required).
   - `R2_ACCOUNT_ID`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, `R2_BUCKET_NAME`, and optional `R2_ENDPOINT` (`https://<R2_ACCOUNT_ID>.r2.cloudflarestorage.com`).
4. **Security Enforcement (RULES §3)**: Public bucket access must remain disabled. Documents are accessed strictly via 5-minute AWS Signature V4 presigned URLs generated by `R2StorageService`, with every admin inspection logged to `verification_access_logs`.

### 2.3 Render Web Services (NestJS API)
Render hosts the backend services with deploy hooks triggered by GitHub Actions.

1. **Staging Service**:
   - Name: `afritrade-api-staging`
   - Branch: `staging`
   - Root Directory: *leave empty*
   - Build Command:
     ```bash
     pnpm install --frozen-lockfile && pnpm --filter @afritrade/shared build && pnpm --filter api build
     ```
     *(Note: `apps/api`'s `build` script executes `prisma generate && nest build`, ensuring Prisma Client is freshly regenerated from `schema.prisma` before NestJS compiles).*
   - Start Command:
     ```bash
     node apps/api/dist/main.js
     ```
   - Environment Variables: `NODE_ENV=staging` (or `production`), `PAYMENTS_MODE=simulated`, `DATABASE_URL` (pooled), `REDIS_URL`, `JWT_ACCESS_SECRET`, `CORS_ORIGINS`, `WEB_APP_URL`.
   - Auto-Deploy: **No** (Deploys are triggered strictly via Deploy Hook to guarantee database migrations finish first).
2. **Production Service**:
   - Name: `afritrade-api-production`
   - Branch: `main` (Auto-Deploy: No).
   - Environment Variables: `NODE_ENV=production`, `PAYMENTS_MODE=simulated` (MVP).
   - Same build and start commands.

### 2.4 Vercel Frontend Deployments (`apps/web` & `apps/admin`)
1. Create projects `afritrade-web` and `afritrade-admin` on Vercel linked to the repository.
2. In Project Settings ➔ General:
   - Framework Preset: `Next.js`
   - Root Directory: *leave empty* (CI script `scripts/ci/vercel-deploy.sh` links each workspace via `.vercel/project.json` and runs with `--cwd apps/web` and `--cwd apps/admin`).
3. Set environment variables for Preview and Production:
   - `NEXT_PUBLIC_API_URL`: Points to corresponding staging/production Render API.
   - `NEXT_PUBLIC_APP_ENV`: `staging` or `production`.
   > [!IMPORTANT]
   > **Do NOT mark `NEXT_PUBLIC_*` environment variables as Sensitive in Vercel.** `NEXT_PUBLIC_*` values are baked into client-side bundles by design. Marking them Sensitive causes `vercel pull` to download the literal string `[SENSITIVE]`.
4. **Concurrency & Serialization**: Vercel Hobby (free) teams allow only 1 concurrent build. CI serializes frontend deployments (`apps/web` then `apps/admin`) with explicit dependencies and 15-minute job timeouts (`timeout-minutes: 15`) to prevent deployments from queueing indefinitely.

## 4. Promotion Lifecycle & Automated Testing

```
feature/* ➔ (PR checks + ephemeral DB integration)
   │
   ▼ Merge to staging
staging ➔ (Checks ➔ Migrate Neon Staging ➔ Seed Staging ➔ Deploy API & Web ➔ Smoke Test)
   │
   ▼ Manual workflow_dispatch: promote_to_main=true, confirm=DEPLOY
production ➔ (Verify staging SHA ➔ Manual Gate ➔ Migrate Neon Prod ➔ Deploy API & Web ➔ Read-Only Smoke ➔ Fast-Forward main)
```

1. **Pre-flight & CI Checks**: Every PR runs policy checks, migration safety checks, typechecking, package unit tests, and production build & boot verification (`verify:prod --quick`).
2. **Ephemeral PR Integration Tests**: When API or shared code changes, GitHub Actions creates an ephemeral branch in Neon (`ci/${run_id}`), runs `migrate:deploy`, executes integration tests, and destroys the branch.
3. **Staging Migration & Seeding**: Every push to `staging` applies pending Prisma migrations and executes `pnpm --filter api seed` to refresh reference data (countries, currencies, rates, sample suppliers, and catalog items).
4. **Automated Smoke Testing**: Staging runs the full auth probe (`smoke-test.mjs --env=staging --auth`), verifying HttpOnly cookies, JWT rotation, and token reuse invalidation. Production runs strictly in read-only mode (`--env=production`).
5. **Cold Starts**: Free web services sleep after inactivity. The health check timeout is set to 180s/600s with retry logic (`wait-for-version.sh`) to accommodate cold-starts gracefully.
6. **Platform Auto-Deploy Disablement & Release Integrity**:
   - **Vercel**: Automatic git-push deployments are disabled via `vercel.json` (`git.deploymentEnabled: false`). Frontend deployments are exclusively driven by the GitHub Actions pipeline using prebuilt CLI deployments (`vercel-deploy.sh`).
   - **Render**: Auto-Deploy must remain set to `No` in the Render dashboard for both API services. API deployments are triggered strictly by GitHub Actions calling the deploy hooks (`RENDER_STAGING_DEPLOY_HOOK`, `RENDER_PRODUCTION_DEPLOY_HOOK`).
   - **`main` Branch Immutability**: Direct PRs and manual merges into `main` are rejected by CI policy. `main` is fast-forwarded only by the automated promotion workflow after production migrations, deploys, and read-only smoke tests pass.
